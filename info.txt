🎯 BINGO WEB APP — Multiplayer Real-time Game (Django + Channels)

Project Overview
A real-time multiplayer Bingo web application where players can create/join rooms, arrange their boards, and play turn-based Bingo with WebSocket-powered live updates.

GitHub Repository: @0luv69/bingo

Layer        Technology

Database     SQLite (dev)
Frontend     Tailwind CSS + Vanilla JavaScript
Real-time    InMemoryChannelLayer (Redis-free single process in dev)
Auth         Django Allauth (Google & GitHub OAuth)

CORE GAME FLOW (CURRENT BEHAVIOR)

1) Create / Join Room
- Host creates a room (public or private) and receives a 6-character room code.
- Room can be shared via code, link, or QR.
- Players join the room and become RoomMembers with roles:
  - host
  - co-host (same permissions as host; mainly for display/labeling)
  - player

Identity / membership
- A RoomMember represents a player’s membership in a Room and survives multiple rounds.
- Player identity is tracked by:
  - authenticated User (if logged in), OR
  - anonymous session_key (Django session) for guests
- The session stores:
  - current_room_code
  - current_member_id
- WebSocket consumer reads current_member_id from the session cookie.

Display name uniqueness
- Display names must be unique per room for active/connected members.
- Rejoin is allowed for the same identity (same user or same session_key) using the same name.
- Name collisions are blocked only when another *different* member is using that name.

2) Lobby / Disconnection Rules
- In the lobby, a player can leave the room.
- If a player disconnects unexpectedly:
  - they become connection_status = "disconnected"
  - a grace period starts
  - after grace period:
    - in lobby/setup: other connected players may vote kick (kick or keep)
    - in playing: the disconnected player becomes bot-controlled so the game continues

3) Setup Phase (Backend-authoritative)
- Board size is N×N (configurable: 5×5 to 10×10).
- Backend starts setup phase and sets a server deadline.
- Players arrange board (drag/drop) and click “Ready”.
- If not all players ready by setup deadline:
  - backend auto-marks all players ready
  - backend transitions to playing phase
- Frontend timers are display-only; backend enforces timing.

4) Playing Phase (Backend-authoritative)
- Turn-based gameplay:
  - current player selects an unmarked number.
  - backend validates it’s their turn and number is allowed.
- If the current player does not act before the turn deadline:
  - backend auto-selects a random available number and calls it.
- When a player disconnects during playing:
  - after grace period they are bot-controlled
  - if it is their turn, backend schedules bot play (auto-call a number)
- Leaving is not allowed as a normal action during playing; disconnect triggers bot behavior.

5) Win Condition
- Required completed lines = board size (e.g., 5 lines for 5×5).
- Winner detection runs after each called number.
- Caller priority rule:
  - If multiple players achieve win simultaneously:
    - if the caller is among winners, caller gets priority and wins.
    - otherwise ties can occur among non-calling winners (e.g., p2+p3 tie).

6) Post-Game
- Winner modal shows final results.
- “Play Again” starts a new round in the same room.
- Room persists across multiple rounds while it remains active.

MEMBER STATUS RULES (IMPORTANT)

RoomMember has fields like:
- is_active (bool)
- connection_status (string) with values like:
  - connected
  - disconnected
  - left
  - kicked
  - banned

Meaning:
- connected: actively online in room
- disconnected: temporarily offline (grace period applies; may become bot-controlled or vote-kicked)
- left: intentionally left; can rejoin later
- kicked: removed temporarily (counts toward ban threshold); can rejoin until banned
- banned: permanently removed; cannot rejoin

Kick escalation:
- kicked_count increments on kicks
- if kicked_count >= 3 → connection_status becomes "banned" and rejoin is blocked

Leave vs Kick:
- Leave means “player opted out” (left) and is allowed to rejoin.
- Kick means “removed by host/admin action” and counts toward a future ban.
- Vote-kick result can be treated like “left” (by current design choice).

Active vs Available members (room capacity & cleanup)
- “Active” refers to is_active=True (can include left if you keep it active for rejoin logic).
- “Available” refers to members who should count toward room being currently occupied (typically connected/disconnected).
- Room cleanup / room-empty checks use “available” count (not just is_active).
- Room-full checks also use “available” count.
